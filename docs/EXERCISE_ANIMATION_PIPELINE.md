# Конвейер 3D-анимаций упражнений TELO365

Этот конвейер добавляет упражнения к двум существующим кандидатам тренера, не создавая заново модели, скелеты, материалы или React Three Fiber viewer. Он предназначен для рабочих и тестовых ассетов; автоматическая проверка **никогда** не утверждает технику и не включает упражнение в основной интерфейс.

## Что считается каноническим

[`trainer/characters.manifest.json`](../trainer/characters.manifest.json) — единственный реестр тестовых персонажей. В нём записаны пути к рабочим `.blend`, test-GLB, SHA-256 моделей, 19 костей, их иерархия и правило совместимости.

При каждой `trainer:verify` система сверяет хеш и скелет модели. Изменение модели или bind pose не проходит незамеченным: ранее созданные клипы нужно заново проверить. Мужчина и женщина используют одинаковую топологию костей, но имеют отдельные bind pose и отдельные экспортированные/ретаргетированные клипы. Нельзя копировать male-анимацию в female-путь без проверки.

## Реестр упражнений

Каждое упражнение описывается файлом `trainer/exercises/<exerciseId>.json`. В нём находятся:

- ID, название, ракурс камеры и описание оборудования/точек крепления;
- отдельные пути к male и female animation GLB;
- длительность, имя клипа, правила loop и политика движения таза;
- технический, визуальный, специалистский и публикационный статусы.

`squat.json` описывает существующие male/female candidates. Они сохраняют статус `visual: pending`, `specialistTechnique: pending`, `readyForPublication: false`, поэтому не являются опубликованной демонстрацией.

## Добавление упражнения

Создай заготовку:

```bash
npm run trainer:new -- --exercise lunge
```

Для безопасной проверки команды можно направить результат в временную папку:

```bash
npm run trainer:new -- --exercise lunge --output artifacts/trainer-smoke
```

Команда проверяет ID, наличие и хеш обоих канонических персонажей, создаёт manifest, два Blender Python-шаблона и инструкцию. Она не создаёт GLB, не копирует приседание и никогда не перезаписывает существующий manifest.

Затем вручную в Blender 5.2+:

1. Открой копию соответствующей рабочей сцены из `characters.manifest.json`.
2. Не меняй геометрию, Armature, bind pose и имена костей канонического персонажа.
3. Создай реальные ключевые позы или выполни ретаргетинг движения отдельно для male и female. В pipeline нет генератора движения по названию упражнения.
4. Проверь промежуточные кадры, стопы, колени, плечи, таз и оборудование. Естественность и корректность техники проверяет человек и специалист.
5. Используй `tools/trainer/exercise_animation_pipeline.py`: `assert_canonical_rig`, `assert_authored_action`, при необходимости `assert_loop`, затем `export_animation_glb`.
6. Сохрани рабочий `.blend` и экспортируй отдельные GLB в пути из manifest. Имя Action/clip должно совпадать с `animation.clip`.
7. Внеси фактическую длительность, ракурс, оборудование и технический статус в manifest только после проверки.

Шаблоны намеренно завершаются ошибкой до появления настоящей авторской анимации. Это защита от появления фиктивного движения в проекте.

### Примеры

| ID | Рекомендуемый контроль перед экспортом |
| --- | --- |
| `squat` | Таз движется контролируемо, стопы устойчивы, цикл не имеет скачка. |
| `pushup` | Боковой ракурс, нейтральная линия корпуса, отдельная проверка плеч и запястий. |
| `plank` | Боковой ракурс, статический или короткий циклический clip; без ложного движения. |
| `dumbbell_row` | Ракурс 3/4, описание гантели и точки крепления; проверь лопатку и нейтральную спину. |
| `shoulder_press` | Ракурс 3/4, описание двух гантелей; проверь траекторию рук и запас над головой. |

## Техническая проверка

```bash
npm run trainer:verify -- --exercise squat
```

Проверка читает manifest и для каждого персонажа подтверждает:

- существование GLB и совпадение хеша канонической модели;
- один `SkinnedMesh`, skin weights, конечные bind matrices, 19 костей и их иерархию;
- существование одного нужного clip, его имя и длительность;
- реальные quaternion tracks, существование всех костей-целей, отсутствие tracks на неописанном root;
- требуемую трансляцию таза, если это задано manifest;
- согласованные первый и последний ключ для loop;
- фактическое применение клипа через `THREE.AnimationMixer`.

Эта команда сообщает только о технической совместимости. Она не меняет JSON-статусы, не оценивает качество движения и не меняет `src/exercise3d.ts`.

Старые адресные проверки остаются обязательными для приседания:

```bash
npm run verify:male-squat-candidate
npm run verify:female-squat-candidate
```

`npm run test:trainer-pipeline` создаёт scaffold во временной папке и удаляет его после проверки: там проверяются защита от перезаписи и отсутствие созданных animation GLB.

## Изолированный preview

Открой `tools/trainer-preview.html` через Vite dev/preview server. Preview читает manifest, позволяет выбрать упражнение и мужского или женского кандидата, использует существующий `Exercise3DViewer` с Play/Pause, 0.5×/1×, Reset, Orbit и touch controls.

Если анимация для выбранного персонажа отсутствует или не прошла технический статус, preview показывает пояснение вместо пустой сцены. Он не подключён к странице тренировок и не меняет production viewer.

## Публикационный шлюз

Даже после успешной технической проверки необходимы:

1. запись `visual: passed` после ручной визуальной проверки;
2. запись `specialistTechnique: passed` после проверки профильным специалистом;
3. технический статус `passed` для обоих персонажей;
4. явная пользовательская команда:

```bash
npm run trainer:publish -- --exercise <id> --approve --apply
```

Команда меняет только publication-state manifest на `approved-for-manual-integration`. Она намеренно не правит `src/exercise3d.ts` и не публикует UI. Отдельное ревьюируемое изменение должно подключить утверждённое упражнение к production viewer.

## Что автоматизировано и что нет

Автоматизированы: контроль ригов/хешей, scaffold, экспортные guard-функции, проверка GLB и isolated preview.

Ручная работа: создание/ретаргетинг движения, подготовка оборудования, коррекция deformations, визуальная оценка, специалистская оценка техники и окончательное решение о публикации.

Публикационная команда перед сменой статуса заново выполняет техническую проверку обоих GLB.
