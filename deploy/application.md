# Серверная версия TELO365

## Состав

- Node.js 24.21.0, ES-модули без сторонних серверных зависимостей.
- SQLite через `node:sqlite`, версия схемы в `PRAGMA user_version`, WAL и внешние ключи.
- Приложение слушает `127.0.0.1:1435`; nginx новой ВМ принимает запросы входного nginx на 8080.
- Код: `/opt/telo365/current` → каталог релиза, владелец root.
- Данные: `/var/lib/telo365/telo365.sqlite`, каталог 0700, база 0600, пользователь `telo365`.
- Сессии на сервере, хеши случайных токенов; production-cookie `__Host-telo365`, Secure/HttpOnly/SameSite=Lax. Пароли — scrypt N=131072/r=8/p=1, случайная соль. Для изменений API проверяются Origin и собственный заголовок. Вход ограничен по адресу и email.

## Установка и обновление

На рабочем компьютере:

```powershell
npm.cmd ci
npm.cmd run build
npm.cmd run test:server
npm.cmd run test:e2e
tar --exclude=*.local -czf telo365-app.tar.gz dist server deploy
scp telo365-app.tar.gz deploy/install-app.sh telo365:/home/max/
```

На новой ВМ:

```bash
sudo bash /home/max/install-app.sh /home/max/telo365-app.tar.gz 192.168.1.180
```

Установщик проверяет состав архива, скачивает закреплённый Node.js с проверкой SHA-256, создаёт системного пользователя, включает systemd и проксирование к приложению. Перед обновлением существующей базы создаётся согласованная копия. При ошибке проверки приложения или nginx возвращаются предыдущий релиз и конфигурация. База не удаляется и не откатывается автоматически. При будущих несовместимых миграциях потребуется отдельный план восстановления данных.

Не использовать прежний `install-site.sh` для обновления серверной версии: он возвращает статическую конфигурацию nginx.

## Управление контентом

Зарегистрировать обычный аккаунт, сохранить резервный код, затем выдать ему роль администратора через консоль:

```bash
sudo -u telo365 env TELO_DB=/var/lib/telo365/telo365.sqlite /opt/telo365/node/bin/node /opt/telo365/current/server/admin.mjs promote EMAIL
```

Первый зарегистрировавшийся автоматически администратором не становится. После обновления страницы администратор увидит «Управление»: описание публичной главной, общие продукты, рецепты, упражнения и программы. Изменения пищевой ценности не переписывают старые записи дневника: в них сохраняется снимок выбранного блюда. Пользователи могут вести отдельный личный каталог продуктов и рецептов.

## Резервные копии

`telo365-backup.timer` ежедневно создаёт согласованную копию SQLite и проверяет `integrity_check`. Каталог `/var/backups/telo365`, права 0700/0600, хранение 14 дней. Ручной запуск:

```bash
sudo systemctl start telo365-backup.service
sudo journalctl -u telo365-backup.service -n 20 --no-pager
sudo systemctl list-timers telo365-backup.timer
```

Копии находятся **на той же ВМ**. Они защищают от ошибки обновления, но не от потери диска хоста. Выгрузка на отдельное хранилище требует выбора и подключения этого хранилища.

Для проверки восстановить копию в новый временный файл через `admin.mjs restore-copy BACKUP NEW_PATH`, проверить `verify-backup NEW_PATH`. Для аварийной замены рабочей базы сначала временно закрыть внешний доступ, выбрать реальную копию и осознанно подтвердить замену:

```bash
sudo bash /opt/telo365/current/deploy/restore.sh /var/backups/telo365/SELECTED.sqlite --confirm-replace
```

Скрипт останавливает приложение, сохраняет прежние данные, проверяет копию, заменяет базу и отзывает восстановленные сессии. Возобновляет приложение и таймеры. При ошибке возвращает прежнюю базу. Перед повторным открытием внешнего доступа нужно повторно применить удаления аккаунтов, выполненные после даты копии: автоматического журнала удалений вне базы пока нет.

## Мониторинг

`telo365-monitor.timer` раз в минуту проверяет HTTP через локальный nginx и запрос к базе. Сбой отражается в статусе systemd/journal. Приложение автоматически перезапускается при аварийном завершении.

```bash
sudo systemctl status telo365 telo365-monitor.timer --no-pager
sudo journalctl -u telo365 -u telo365-monitor.service -n 50 --no-pager
curl --fail http://127.0.0.1:8080/api/health
```

Внешний мониторинг интернета, сообщения оператору и проверка срока TLS не подключены. Ошибки локального timer не отправляются по почте.

## Почта и тестовый ящик

Приложение умеет подтверждать адрес и восстанавливать пароль по одноразовым ссылкам. Ссылки подтверждения действуют 24 часа, сброса — 30 минут; они не хранятся в базе в открытом виде и после применения отзывают активные сеансы. Резервный код остаётся рабочим способом восстановления.

Для безопасной разработки на ВМ установлен Mailpit: TELO365 использует loopback SMTP `127.0.0.1:1025`, интерфейс ящика — `127.0.0.1:8025`. Он не имеет внешнего маршрута и не отправляет письма в интернет. Включить этот режим:

```bash
sudo install -d -m 700 /etc/telo365
sudo tee /etc/telo365/mail.env >/dev/null <<'EOF'
MAIL_MODE=capture
MAIL_HOST=127.0.0.1
MAIL_PORT=1025
MAIL_PUBLIC_URL=https://telo365.ru
MAIL_FROM=no-reply@telo365.ru
EOF
sudo chmod 600 /etc/telo365/mail.env
sudo systemctl restart telo365
```

Посмотреть тестовые письма с рабочего компьютера, не открывая ящик в интернет:

```powershell
ssh -L 8025:127.0.0.1:8025 telo365
```

После этого открыть `http://127.0.0.1:8025`. Туннель держать открытым только во время просмотра. Переход к настоящей доставке требует отдельного SMTP-провайдера, SMTP credentials в `/etc/telo365/mail.env` с правами 0600, SPF/DKIM/DMARC у домена и смены `MAIL_MODE=smtp`. Не публиковать Mailpit и не включать relay для тестовой установки.

## Обычное обслуживание без пароля sudo

На этой ВМ `max` может вызвать только root-owned wrapper: `sudo /usr/local/sbin/telo365-admin restart`, `backup`, `mail-restart`, `status` или `health`. Он не принимает произвольные команды. Установка нового релиза по-прежнему требует sudo-пароль: архив релиза содержит systemd/nginx-конфигурацию, поэтому разрешение установки без контроля давало бы полный доступ к root.

## Ограничения ранней версии

- Email используется как логин. В тестовом режиме письма остаются в закрытом Mailpit; внешняя отправка и подтверждение доставляемости адресов ещё не включены. Резервный код остаётся доступен и после использования заменяется новым.
- Начальный каталог — помеченные учебные примеры. Для публичного продукта нужны проверенные данные продуктов и подготовленные программы тренировок.
- Нет платежей/PRO, загрузки фото, автоматического назначения питания и интеграций с магазинами/трекерами.
- Личные данные доступны только после входа. В профиле предусмотрены экспорт JSON и удаление аккаунта. Публичное описание данных — `/privacy`; сведения об операторе и окончательные условия открытого сервиса требуют заполнения владельцем.
- Серверные тесты проверяют права доступа, защиту запросов, восстановление, снимки блюд, агрегацию покупок и сохранность базы. Браузерные — сквозной пользовательский сценарий desktop/mobile и отдельное демо.
